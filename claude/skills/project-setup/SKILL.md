Set up the current project so Claude Code can work in it and check its own work. Keep the core small and the same everywhere: instruction pointer, `.env` deny, the verification command(s), `.gitignore` lines. Rules that differ per project (style, layout, tool quirks) go in path-scoped rules, and only where the project's own files show them; this skill carries no stack defaults. Base every line on files you read; never invent a command. Anything you cannot confirm goes in the final "Not verified" list. Do not open `.env*` or credential files; name them only. Write your reports and questions in the language the global `CLAUDE.md` sets for replies, even though this skill is written in English. Notes from the user: $ARGUMENTS

1. Preconditions. Confirm the working directory is a git repository root (`git rev-parse --show-toplevel`); if not, stop and ask. If a `CLAUDE.md` or `.claude/` already exists, improve it as a diff instead of overwriting it. Note which of `AGENTS.md` and `CLAUDE.md` exist; step 5 depends on it. If both exist with identical content, ask whether `CLAUDE.md` is a symlink to `AGENTS.md`, and never write through a symlink.
2. Read the global layer first: `CLAUDE.md` and `settings.json` in `${CLAUDE_CONFIG_DIR:-~/.claude}`, plus the names of its skills and agents. They already apply to every project, so Claude-only project files must not restate them (`AGENTS.md` is different, see step 5). If the directory is missing, say so in "Not verified" and continue.
3. Detect the stack by reading manifests and config: `package.json`, `composer.json`, `pyproject.toml`, `requirements*.txt`, `go.mod`, `Gemfile`, `pom.xml`, `Makefile`, lint and format configs (`.editorconfig`, eslint, prettier, stylelint, phpcs), and file extensions. Classify the areas present: markup and styles (html, css, scss, templates), frontend (js, ts, jsx, tsx, vue), backend (php, py, go, java, rb, cs). Report what you found.
4. Find the verification commands per area. Read them from `package.json` scripts, `composer.json` scripts, `Makefile` targets, test configs, and `.github/workflows/*` (what CI runs is the best source). If an area has no check you can find, ask the user what it should be (tests, lint, build, or a screenshot comparison for visual work). Do not make one up. Then propose how hard the check gates the work and let the user pick: (a) a line in `CLAUDE.md` telling Claude to run it before reporting done (default), (b) a `/goal` condition per session, (c) a Stop hook that blocks until it passes, (d) a fresh-context reviewer subagent. Add a hook only if the user picks (c).
5. Draft the instruction files by what step 1 found. Never edit, shorten or delete `AGENTS.md`: other tools (Codex) read it and do not read the global layer, so the "do not restate" rule covers Claude-only files alone.
   - `AGENTS.md` only: do not create a `CLAUDE.md` that copies it; Claude Code reads `AGENTS.md` when no `CLAUDE.md` exists. Propose the `.claude/` files below. The verified commands, the gate line from step 4 and the container-or-host note need a home: ask which the user prefers, (i) a minimal `CLAUDE.md` whose first line is `@AGENTS.md` followed by those lines (a `CLAUDE.md` without that import makes Claude stop reading `AGENTS.md`), or (ii) lines the user adds to `AGENTS.md` themselves.
   - Both files: `AGENTS.md` is the source. Propose `CLAUDE.md` as `@AGENTS.md` plus a few Claude-only lines (an import, not a symlink: symlinks break on Windows); keep any Claude-only content the current `CLAUDE.md` really has. List every `[REPLACE:` placeholder you see without filling it. If `CLAUDE.md` is over 200 lines, propose moving area rules into step 6's path-scoped rules. If `AGENTS.md` is over 200 lines, only report its length.
   - `CLAUDE.md` only, or neither: draft `CLAUDE.md`, under 200 lines. Include only what Claude cannot learn from the code and the global layer: the verified commands, cross-area style rules that differ from the defaults (from the configs you read), repository etiquette found in README or CONTRIBUTING, and real gotchas; rules for one area go in step 6 instead. For each line ask whether removing it would cause a mistake; if not, drop it. End the workflow section with: run the verification before reporting done.
   - In every case: if `docker-compose.yml` or a `makefile` exists, state whether the verified commands run in the container or on the host, in the file the user chose above. For `AGENTS.md` it is only a line the user adds themselves; you never write it.
6. Draft path-scoped rules in `.claude/rules/<area>.md` only for an area that has rules of its own. Use exactly this frontmatter (`paths` is the only field Claude Code reads, as a YAML list of globs):
   ```
   ---
   paths:
     - "src/**/*.{ts,tsx}"
   ---
   ```
   Do not create a rule file that would only repeat `CLAUDE.md`.
7. Draft `.claude/settings.json` with `permissions.deny` for `Read(**/.env*)`, `Read(**/.credentials*)` and `Read(**/credentials.json)`. This repeats the global deny on purpose: cloud sessions and teammates do not read `~/.claude`. Add `permissions.allow` for the verified read-only check commands (test, lint, typecheck); leave out builds and anything else that writes files. It matters most for teammates and cloud (narrow allow rules still apply in auto mode; broad ones are suspended). If `rtk` is on PATH (`command -v rtk`), add the `rtk ` twin of every Bash rule. Never allow destructive commands, never set `defaultMode`, and never set a bypass or auto mode.
8. Propose `.gitignore` lines for `CLAUDE.local.md`, `.claude/settings.local.json` and `.claude/handoff.md` (the global handoff note, never committed) if they are absent.
9. Plugins: do not install or recommend any plugin.
10. Show every file you propose in full (or as a diff for existing files) and wait for an explicit yes. Write only what was approved; permission prompts may be off, so this step is the approval.
11. Finish with: the files written, what the user should check in a new session (`/context` lists the project `CLAUDE.md`, `/hooks` shows only intended hooks, `/doctor` suggests cuts), and a "Not verified" list.
